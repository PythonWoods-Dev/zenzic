## Rationale

This system rule is emitted when a file's parallel-mode worker process fails to complete within the execution timeout budget — a **file-level** stall, not a per-rule one. It only applies in parallel scan mode (1000+ files); sequential-mode scans have no worker process to stall.

`[[custom_rules]]` regex patterns cannot cause this: they compile with Google RE2 (ZRT-007), a DFA engine with no backtracking — catastrophic-backtracking ReDoS is not possible for them. A stall is typically an I/O hang, a network stall, a worker process crash, or (for an installed Python plugin rule via the `zenzic.rules` entry-point group, distinct from TOML regex rules) genuinely slow or blocking code inside that plugin's `check()` method.

Zenzic enforces this execution bound to prevent a single stalled worker from hanging the entire continuous integration build pipeline.

---

## How to Fix

If using a Python plugin rule, check it for slow I/O, network calls, or other blocking operations inside `check()`. Rule out a transient environment issue (disk contention, network latency) first — Z902 is more often a systemic stall than a rule-authoring bug. `[[custom_rules]]` regex patterns are not a possible cause, since RE2 rejects unsafe patterns at config-load time, before this timeout mechanism is ever reached.

The per-file worker timeout is a fixed, non-configurable engine constant (`_WORKER_TIMEOUT_S = 30` seconds) — there is no `.zenzic.toml` key to raise or lower it.
