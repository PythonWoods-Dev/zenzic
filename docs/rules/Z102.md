## Rationale

This rule is emitted when an inline link targets a fragment identifier (`#anchor-name`), but the destination document contains no heading slug or explicit anchor ID matching that fragment.

Fragment links pointing to missing anchors navigate to the page top but fail to jump to the intended topic section, degrading reading experience.

### What the anchor is compared against, and when that is a prediction

Zenzic does not render your site, so it computes the slug a heading *would* publish under
and compares the fragment to that. **Which slug it computes depends on the engine you
declared**, and only two of the answers are measured against the real renderer:

| Declared engine | The slug is | Confidence |
| :--- | :--- | :--- |
| `mkdocs`, `zensical` | Python-Markdown's `toc` slugify, or `pymdownx.slugs.slugify` when the project enables it — both reproduced and compared against the real library on every test run | **Measured.** See [tested versions](../reference/compatibility.md#libraries-zenzic-reproduces-rather-than-imports) |
| `prebuilt`, `standalone` | Python-Markdown's slug, because there is nothing else to go on | **Predicted.** `prebuilt` means *a generator Zenzic does not model* — Astro and Docusaurus use `github-slugger`, whose output differs |

**So a `Z102` on a `prebuilt` project may be a renderer divergence rather than a broken
link**, and that is a declared limit rather than a defect to report. The route manifest a
`prebuilt` project supplies carries `url`, `status` and `slug` — it does **not** carry
anchors, which is the only artefact that would settle the question without Zenzic modelling
someone else's slugger.

If a `Z102` looks wrong on such a project, check the anchor the generator actually
publishes before treating it as a finding. On `mkdocs` and `zensical` the comparison is
against the library itself, and a disagreement there is worth reporting.

---

### Suppressing it on an HTML tag

When the link is written as a raw HTML tag rather than Markdown, the
parameterless `data-zenzic-ignore` attribute on that tag suppresses `Z102`:

```html
<a href="./missing-page.md" data-zenzic-ignore>Label</a>
```

This works only for an HTML tag — a Markdown link carries no attribute to put it
on, and is governed by an inline `<!-- zenzic:ignore: Z102 -->` comment or by
`.zenzic.toml` instead. The attribute covers the HTML hygiene tier
(`Z120`–`Z124`) and the relative-link tier (`Z102`, `Z104`, `Z105`); it does
**not** cover [`Z101`](Z101.md), which is decided against the Virtual Site Map
rather than against the tag. **A tag with a missing `.md`-page target can
therefore raise `Z101` with the attribute present** — the two codes are
suppressed by different mechanisms. An attribute that suppresses nothing is
itself reported as [`Z603`](Z603.md).

## How to Fix

Inspect the flagged location in the Markdown file and update the content or configuration:

<div class="grid cards zz-pattern-pair" markdown>

- :material-close-circle:{ .lg .middle style="color: var(--zz-error);" } **Failing Pattern (Triggers Z102)**

    ---

    ```markdown title="docs/guide/example.md"
    <!-- BAD: Anchor fragment #security-gate does not exist on target page -->
    See the [Security Gate Options](../how-to/configure-privacy-gate.md#security-gate).
    ```

- :material-check-circle:{ .lg .middle style="color: var(--zz-success);" } **Passing Pattern (Resolves Z102)**

    ---

    ```markdown title="docs/guide/example.md"
    <!-- GOOD: Target page contains explicit anchor attribute -->
    ## Security Options {#security-gate}

    Configure privacy gate settings below...
    ```

</div>

---

## Configuration

Same-page anchor validation always runs; there is no configuration flag to
disable it.
