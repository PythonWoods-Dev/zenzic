What Zenzic Reads

Four ways in. Your stack is probably one of them.

Zenzic resolves every link against the site your build actually publishes. How it learns that structure depends on the engine — and for generators that decide it at build time, on the route manifest they already emit.

01

MkDocs

Reads mkdocs.yml and its navigation tree, so links, anchors and orphans are resolved against the site the build produces rather than against the file tree.

mkdocs.yml · adapter run 
# MkDocs project
uvx zenzic check all .

# Outcome
# exit 0 -> no blocking findings
# exit 1 -> quality gate blocks merge
02

Zensical

Reads zensical.toml and its navigation output, with the same routing model as MkDocs and no build step required to analyse it.

zensical.toml · adapter run 
# Zensical project
uvx zenzic check all .

# Output is machine-readable and human-readable
# for CI and local review
03

Standalone Markdown

Repositories with no framework-specific adapter, where the directory layout is the structure. Nothing to configure and nothing to install into the project.

standalone repository · adapter run 
# Plain Markdown repository
uvx zenzic check all docs/

# Use in CI, pre-commit, or local checks
# without changing repository structure
04

Generators That Publish a Route Manifest

A site whose structure is decided at build time is read through the routes its own build writes, not through a re-implementation of its routing. Declare the prebuilt engine and point it at a .zenzic-vsm.json your generator emits. Verified against Astro and Docusaurus; the manifest is required, and a declared prebuilt without one stops with a configuration error rather than quietly analysing something else.

.zenzic-vsm.json · prebuilt run 
# .zenzic.toml
[build_context]
engine = "prebuilt"

# Your build writes .zenzic-vsm.json
uvx zenzic check all
